# Лабораторная работа №3 — DevOps

**Вариант 36.** Веб-интерфейс для просмотра динамики количества подтверждённых бронирований и выручки по дням, неделям или месяцам за выбранный период создания бронирований. Задание: [Issue #1](https://github.com/rteats/MPEI-DevOps-Lab3/issues/1).

Реализована небольшая панель аналитики. Фронтенд написан на HTML, CSS и JavaScript без сторонних библиотек. Бэкенд не изменяется: используется готовый образ из проекта [nelkor/moscow-events](https://github.com/nelkor/moscow-events).

## Запуск

Нужны установленный Docker и Docker Compose. Из корня проекта выполните:

```bash
docker compose up -d
```

После запуска откройте **http://localhost:8080**. При первом запуске скачиваются образы, запускается PostgreSQL, затем бэкенд создаёт таблицы и добавляет демонстрационные данные. Фронтенд запускается после готовности бэкенда. Дополнительные команды и настройка окружения не требуются.

Для остановки контейнеров:

```bash
docker compose down
```

Чтобы остановить проект **и удалить сохранённую базу данных** (все изменения будут потеряны):

```bash
docker compose down -v
```

## Работа с интерфейсом

1. Выберите даты **«Дата с»** и **«Дата по»**. Обе даты включаются в отчёт. Можно быстро задать последние 7, 30 или 90 дней относительно выбранной даты окончания.
2. Переключайте группировку **«Дни»**, **«Недели»**, **«Месяцы»**. Неделя начинается с понедельника.
3. Нажмите **«Показать отчёт»**. На экране появятся общие показатели, два графика (количество броней и выручка) и таблица по периодам.
4. В таблице можно включить пустые периоды. Кнопка **«Скачать CSV»** экспортирует отображаемые строки с числами без форматирования; файл открывается в Excel.
5. Кнопка «Обновить» повторяет запрос к API. При ошибке соединения выводится сообщение и кнопка повтора.

Начальный период определяется автоматически из последнего месяца бронирований в базе (90 дней до конца этого месяца). Если бронирований нет, используется `reference_time` из API. Поэтому демонстрационный набор за 2027 год виден независимо от текущей даты компьютера.

## Как работает Docker Compose

В `compose.yml` описаны три сервиса:

- **db** — образ `postgis/postgis:17-3.6`: PostgreSQL 17 с расширением PostGIS. База хранится в именованном томе `db_data`, чтобы данные сохранялись после перезапуска контейнеров.
- **backend** — готовый образ `ghcr.io/nelkor/moscow-events:latest`. Переменные `PG_*` передают адрес БД, имя базы, пользователя и пароль. `SEED_MODE=sample` добавляет демонстрационные записи только в пустую БД.
- **frontend** — `nginx:stable-alpine`. Монтирует каталог `frontend/` и файл `nginx.conf` в режиме чтения. Порт компьютера `8080` перенаправлен на порт `80` контейнера NGINX.

`depends_on` с условием `service_healthy` задаёт порядок запуска: сначала готовность PostgreSQL, затем готовность API, затем NGINX. Все три сервиса находятся в одной сети, которую Compose создаёт автоматически. Поэтому NGINX обращается к API по имени `backend:8000`, а бэкенд — к базе по имени `db:5432`. Порты базы данных и бэкенда наружу не публикуются.

Указанные в Compose логин и пароль — **демонстрационные** для локальной лабораторной работы, не для публичного развёртывания. Для реального размещения необходимы отдельные секреты и настройки безопасности.

## Откуда берутся показатели

Фронтенд обращается к `GET /api/v1/analytics/reservations` с параметрами:

| Параметр | Значение |
| --- | --- |
| `group_by` | `day`, `week` или `month` |
| `booked_from` | Начало выбранной даты в московском времени, включительно |
| `booked_to` | Начало дня **после** выбранной даты окончания в московском времени, не включая его |
| `metrics` | `reservation_count,sold_tickets,revenue_rub` |

Например, для выбранного **1 марта 2027 года** запрос выглядит так (в строке URL символ `+` кодируется как `%2B`):

```text
/api/v1/analytics/reservations?group_by=day&booked_from=2027-03-01T00%3A00%3A00%2B03%3A00&booked_to=2027-03-02T00%3A00%3A00%2B03%3A00&metrics=reservation_count%2Csold_tickets%2Crevenue_rub
```

Бэкенд сам считает агрегаты по **всей отфильтрованной выборке**:

- `reservation_count` — количество бронирований со статусом `confirmed`;
- `revenue_rub` — сумма их `total_price_rub` по цене на момент создания, в рублях;
- `sold_tickets` — сумма `quantity` по подтверждённым броням.

Отменённые брони в этих метриках не учитываются. Средний чек рассчитывается на фронтенде как `revenue_rub / reservation_count`. Сервер группирует даты в часовом поясе `Europe/Moscow` (UTC+3), недели — с понедельника. Если API не вернул строку для дня, недели или месяца, фронтенд отображает ноль. Это не прогноз и не подмена данных: в указанном интервале для такого периода нет подтверждённых бронирований.

Запросы идут с того же домена и порта, что и сайт, по относительному пути `/api/v1/...`. NGINX перенаправляет их в контейнер бэкенда — поэтому отдельная настройка CORS не нужна.

Документация серверного API доступна по [http://localhost:8080/docs](http://localhost:8080/docs). Исходная спецификация — [OpenAPI преподавателя](https://github.com/nelkor/moscow-events/blob/main/docs/openapi.yml).

## Проверка и поиск ошибок

Локальные проверки расчётов выполняются при установленном Node.js 20+:

```bash
node --test tests/analytics.test.mjs
```

Запуск самих контейнеров и проверка статусов:

```bash
docker compose ps
docker compose logs backend
docker compose logs db
docker compose logs frontend
```

Проверить готовность API можно через `http://localhost:8080/health/ready`. Он возвращает HTTP 200 и `{"status":"ready"}` после подключения к БД.

Если порт `8080` занят, поменяйте в `compose.yml` строку `8080:80`, например на `8081:80`, и откройте `http://localhost:8081`.
